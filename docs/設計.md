# Phase 2 設計書 — データパイプライン ＆ AI分析エンジン

## 1. 目的

ティッカー入力および PDF ドロップから、各種財務データ・一次資料テキストを取得し、
LLM（OpenAI / Anthropic / Gemini / OpenAI互換API）へ安全に渡して
**20項目のファンダメンタル分析**を生成・表示する。

---

## 2. 実装モジュール構成

| # | モジュール | 配置 | 役割 |
| --- | --- | --- | --- |
| 1 | API Key & Config Manager | `src/lib/config/` | 設定モーダル、APIキーの保持、プロバイダー選択状態の管理 |
| 2 | LLM Unified Engine | `src/lib/llm/` | OpenAI / Anthropic / Gemini / Custom の共通インターフェース |
| 3 | Financial Data Fetcher | `src/lib/api/` | Yahoo Finance（指標）/ SEC EDGAR（10-K・10-Q 本文） |
| 4 | PDF / Document Parser | `src/lib/parser/` | PDF テキスト抽出、トークン数カウンター、オーバーフロー警告 |
| 5 | Prompt Engine & Pipeline | `src/lib/prompts/` | 20項目プロンプトのパッキング、Markdown テーブルのパース |

## 4. アーキテクチャ上の重要な決定

設計書の「モジュール構成」は `src/lib/` 配下に維持しつつ、
**実際のネットワーク呼び出しと秘密情報の保持は Rust（`src-tauri/`）側で行う。**
`src/lib/` の各モジュールは Tauri コマンドを呼ぶ薄いラッパとなる。

### 4.1 なぜ HTTP を Rust 側に置くのか

| 理由 | 詳細 |
| --- | --- |
| **CORS** | Yahoo Finance / SEC / 各 LLM API は WebView からの直接リクエストを CORS で拒否する |
| **User-Agent** | SEC EDGAR は連絡先入りの `User-Agent` を必須とするが、ブラウザは User-Agent の変更を禁止している |
| **秘密情報** | APIキーを WebView に渡さずに済む。キーは OS のアプリ設定ディレクトリに置き、フロントへはマスク済み文字列のみ返す |
| **Cookie** | Yahoo Finance の `crumb` 取得には Cookie セッションの保持が必要 |

```
┌─ フロントエンド (WebView) ────────────────┐
│  src/lib/config  src/lib/llm             │
│  src/lib/api     src/lib/parser          │  ← 実キーを一切保持しない
│  src/lib/prompts                         │
└───────────────┬──────────────────────────┘
                │ invoke() / Channel（ストリーミング）
┌───────────────▼──────────────────────────┐
│  src-tauri/src/                          │
│    settings.rs  … キー保存・マスク         │
│    llm/         … 4プロバイダ + SSE       │
│    yahoo.rs     … 指標取得（crumb 対応）   │
│    edgar.rs     … 10-K / 10-Q 本文        │
│    html.rs      … HTML → テキスト          │
└──────────────────────────────────────────┘
```

### 4.2 PDF パーサは `pdfjs-dist` を使う

設計書では `pdf-parse` を指定しているが、`pdf-parse` は Node.js 専用で `fs` に依存するため
WebView（ブラウザ環境）では動作しない。クライアントサイド抽出の標準である
**`pdfjs-dist`** を採用する。抽出はフロント側で完結し、PDF の中身はディスクに残さない。

### 4.3 `temperature: 0.0` の扱い

決定論的出力のため `temperature: 0.0` を固定するが、**プロバイダによって扱いが異なる**。

| プロバイダ | temperature | 備考 |
| --- | --- | --- |
| OpenAI | `0.0` を送信 | |
| Gemini | `0.0` を送信 | |
| OpenAI互換 (DeepSeek 等) | `0.0` を送信 | |
| Anthropic | **送信しない** | Claude Opus 5 では `temperature` パラメータ自体が廃止され、送ると HTTP 400 になる。深さの制御は `output_config.effort` で行う |

## 6. Step 1 詳細設計（実装済み）

### 6.1 設定の保存場所

```
%APPDATA%\com.stockanalyzer.desktop\settings.json
```

- APIキーはこのファイルにのみ存在し、**フロントエンドへは生の値を返さない**
- フロントへ返すのは `configured: boolean` と `masked: "sk-…3f9a"` のみ
- `.env` の `VITE_*` 方式（Phase 1 の暫定実装）は廃止

### 6.2 設定項目

| 項目 | 内容 |
| --- | --- |
| プロバイダ選択 | 組み込み 3 種 + ユーザーが追加した OpenAI互換プロバイダ |
| APIキー | プロバイダごとに 1 つ（カスタムも同じ辞書で管理） |
| モデル名 | プロバイダごとに 1 つ |
| SEC User-Agent | `アプリ名 メールアドレス` 形式。SEC が必須とする |
| 最大プロンプトトークン | プロンプトパッキングの上限（既定 180,000） |

#### プロバイダのデータモデル

プロバイダは 2 種類に分かれる。

| 種別 | ID | 追加・削除 |
| --- | --- | --- |
| 組み込み | `openai` / `anthropic` / `gemini`（固定） | 不可 |
| OpenAI互換 | `custom-<採番>` | **可変長リスト。UI から自由に追加・削除できる** |

```rust
struct CustomProvider { id, label, base_url, model }

struct Settings {
    provider: String,                    // 組み込み ID または カスタム ID
    models: BTreeMap<String, String>,    // 組み込みのモデル名
    keys: BTreeMap<String, String>,      // プロバイダ ID → APIキー（組み込み・カスタム共通）
    custom_providers: Vec<CustomProvider>,
    ...
}
```

- APIキーは**組み込み・カスタムを区別せず同一の辞書**で管理するため、
  マスク表示・保存・削除のロジックが 1 本で済む。
- カスタム枠を削除すると、対応する APIキーも同時に破棄される。
- 選択中のプロバイダを削除した場合は組み込みへ自動的に戻す。
- 旧形式（カスタム枠が 1 つ固定だった頃の `custom_base_url`）は
  設定読み込み時に自動でリストへ移行する。
- カスタムプロバイダを配列として保持することで、
  将来の**複数 LLM の直列/並列検証**から個別に呼び出せる。

### 6.3 LLM Unified Engine

`src-tauri/src/llm/` に 4 プロバイダの実装を置き、共通の `LlmRequest` を受けて
**Tauri の Channel でトークンをストリーミング**する。

```
LlmRequest { provider?, system?, messages[], maxTokens? }
   ↓ invoke("llm_send", { request, onEvent: Channel })
LlmEvent = Start  { provider, model }
         | Delta  { text }        ← 逐次描画
         | Done   { text, ... }
         | Error  { message }
```

| プロバイダ | エンドポイント | 認証ヘッダ | ストリーム形式 |
| --- | --- | --- | --- |
| OpenAI | `POST /v1/chat/completions` | `Authorization: Bearer` | SSE `choices[0].delta.content` |
| Anthropic | `POST /v1/messages` | `x-api-key` + `anthropic-version` | SSE `content_block_delta.delta.text` |
| Gemini | `:streamGenerateContent?alt=sse` | `x-goog-api-key` | SSE `candidates[0].content.parts[].text` |
| OpenAI互換 | Base URL + `/chat/completions` | `Authorization: Bearer` | OpenAI と同形式（実装を再利用） |

Anthropic 固有の扱い:
- `temperature` は送らない（400 になるため）
- `output_config.effort` で思考の深さを制御
- `stop_reason: "refusal"` を検知してユーザーに通知
- `fallbacks: "default"` を有効化し、拒否時に自動で代替モデルへ回す

### 6.4 UI

- **設定モーダル**: メニューバーの「ファイル > 設定…」「ヘルプ > …」、および
  上部の APIキー状態インジケーターのクリックで開く
- **対話パネル**: メイン下部のスプリット右側。テストメッセージを送信して
  ストリーミング応答を確認できる（疎通確認）

## 6.5 Step 2 詳細設計（実装済み）

### Yahoo Finance

`quoteSummary` は 2024 年以降 Cookie と crumb（CSRF トークン）を要求する。手順は次のとおり。

```
1. GET https://fc.yahoo.com/                       → Cookie を受け取る（404 が正常）
2. GET .../v1/test/getcrumb                        → crumb（プロセス内にキャッシュ）
3. GET .../v10/finance/quoteSummary/{symbol}?...&crumb=...
   → 401 なら crumb を捨てて 1 回だけ再取得
```

株価だけは crumb 不要の `chart` エンドポイントからも取れるため、
**`quoteSummary` が失敗しても株価・銘柄名・通貨は返す**（`warning` に理由を入れる）。

取得する指標は 6 グループ 36 項目。

| グループ | 項目 |
| --- | --- |
| 株価・規模 | 時価総額 / EV / 52週安値・高値 / ベータ / 発行済株式数 |
| バリュエーション | PER（実績・予想）/ PBR / PSR / EV·EBITDA / EV·売上高 |
| 成長性 | 売上成長率 / EPS成長率 / 四半期利益成長率 / EPS（実績・予想）/ 売上高 |
| 収益性 | 粗利率 / 営業利益率 / 純利益率 / EBITDAマージン / ROE / ROA |
| キャッシュ・財務健全性 | フリーCF / 営業CF / 現金 / 有利子負債 / D/E / 流動比率 |
| アナリスト予想 | 目標株価（平均・高・低）/ レーティング / 推奨スコア / アナリスト数 |

割合の扱いに注意が必要。Yahoo は `returnOnEquity` などを小数（0.4523）で返す一方、
`debtToEquity` は既に百分率（78.445）で返すため、整形関数を分けている。

### SEC EDGAR

**本文をダウンロードしない軽量なステータス照会**（`fetch_status`）を追加した。
`submissions/CIK##########.json` の `filings.recent` を走査し、
10-K / 10-Q の最新 1 件（提出日・対象期間・URL）だけを返す。

「EDGAR に登録がない」「User-Agent 未設定」は**エラーではなく状態として**返す。
非米国上場銘柄（例: 7203.T）でも Yahoo の指標表示を止めないため。

| `status` | 意味 | インジケーター |
| --- | --- | --- |
| `ok`（10-K と 10-Q 両方） | 分析に必要な資料がそろっている | 🟢 |
| `ok`（片方のみ） | 一部のみ取得可能 | 🟡 |
| `userAgentMissing` | 設定すれば取得できる | 🟡 |
| `noFilings` | 直近に 10-K / 10-Q がない | 🟡 |
| `notInEdgar` | 構造的に取得不可（非米国上場など） | 🔴 |

## 6.6 Step 3 詳細設計（実装済み）

### テキスト抽出（フロント側で完結）

| 形式 | 実装 |
| --- | --- |
| PDF | `pdfjs-dist`（1MB 超あるため**動的 import** で PDF が来たときだけ読み込む） |
| DOCX | `fflate` で ZIP を展開し `word/document.xml` からタグ除去 |
| HTML | `DOMParser` で script/style を除去して textContent |
| TXT / MD / CSV / JSON | そのまま読み込み |

ファイルは外部に送信されず、抽出はすべて WebView 内で完結する。
PDF は `--- p.N ---` のページ区切りを入れて出典を追えるようにしている。

### ステージング（Rust 側で永続化）

```text
<app_data_dir>/temp_documents/
  ├── index.json   … メタデータ一覧
  ├── doc-<nanos>.txt … 抽出済みテキスト
  └── …
```

**保存するのは抽出済みテキストとメタデータのみで、元のバイナリは複製しない。**

理由:
- LLM に渡すのはテキストであり、原本はユーザーのディスクに残っている
- HTML5 のドロップではファイルの絶対パスが取れないため、原本を保存するには
  バイト列を IPC で渡すことになり、10MB の PDF が JSON 配列で 30MB 超になって遅い
- 結果としてキャッシュが小さく、取り込みが即座に終わる

要件（プレビュー / リネーム / 削除 / 再起動後の保持）はテキストとメタデータだけで満たせる。

### トークン概算

正確なトークン数はモデルのトークナイザ依存のため、次の規則で概算する。

```
概算トークン = CJK文字数 + ceil(その他の文字数 / 4)
```

CJK（漢字・かな・ハングル・全角形）は 1 文字 ≒ 1 トークン、英数字は 4 文字 ≒ 1 トークン。
同じ規則を Rust（`documents.rs::estimate_tokens`）と TS（`tokenCount.ts`）の両方に置いている。

インジケーターの閾値:

| 消費率 | 表示 |
| --- | --- |
| < 75% | 🟢 余裕あり |
| 75% 〜 100% | 🟡 入力上限に接近 |
| ≧ 100% | 🔴 入力上限を超過 |

上限は設定の `maxPromptTokens`（既定 180,000）を使う。

### UI 配置

ドロップゾーンの**直下**に「一時保存中の資料」トレイを置き、常に状況が見えるようにした。

```
┌ CommandBar ─ ティッカー入力 │ ドロップゾーン │ APIキー状態 ┐
├ DocumentTray ───────────────────────────────────────────┤
│ 一時保存中の資料 [3]  🟢 file.pdf 12.4k ✕  …  ▓▓▓░ 45k/180k  一括クリア │
└─────────────────────────────────────────────────────────┘
```

- チップをクリック → プレビューモーダル（抽出テキスト全文）
- チップをダブルクリック → その場でリネーム（Enter 確定 / Esc 取消）
- ✕ → 個別削除、「一括クリア」→ 全削除

### 既知の制限

- 画像のみの PDF（スキャン資料）は OCR を行わないためテキストを抽出できない。
  その場合は取り込み時にエラーを返す
- `standardFontDataUrl` を指定していないため pdfjs が警告を出すことがあるが、
  テキスト抽出には影響しない（検証済み）

## 6.7 Step 4 詳細設計（実装済み）

### プロンプトの組み立て

```
buildAnalysisPrompt({ ticker, fundamentals, filing, documents, tokenLimit, reserveForOutput })
  ↓
system … 20項目の定義 + スコア尺度 + 出力フォーマット（厳守事項つき）
user   … # 分析対象 / ## 財務指標 / ## SEC提出書類 / ## 添付された一次資料
```

**トークン予算の配分**（優先度順）

| 優先度 | 内容 | 扱い |
| --- | --- | --- |
| 1 | 財務指標 | 小さいので常に全量 |
| 2 | ユーザーが投入した一次資料 | 意図的に選ばれたものなので優先（残余の 55%） |
| 3 | SEC 提出書類 | 最も大きいので最初に切り詰める（残余の 45%） |

- 片方が枠を使い切らなければ、余りをもう片方へ回す
- 添付資料は「均等割り → 収まる資料は全量 → 余りを溢れる資料へ再配分」
- SEC 本文は **Item 1A. Risk Factors / Item 7. MD&A / Item 1. Business** 等の
  分析価値が高い節を優先的に抜き出し、それでも入らなければ各節を前後で切り詰める
- 最後に全体で検算し、まだ超えていれば user 部分をさらに削る（`enforceLimit`）

> **文字数への逆算に注意。** CJK は 1 文字 ≒ 1 トークン、英数字は 4 文字 ≒ 1 トークンなので、
> 固定係数で「トークン → 文字数」を計算すると日本語資料で大幅に超過する。
> 実装では**その文章自身の「文字あたりトークン数」から逆算**している。

### 出力フォーマットとパース

LLM には次の構造を厳守させ、`parseAnalysis.ts` で構造化する。

```markdown
## 評価テーブル
| # | 項目 | スコア | 評価 | 根拠 |
（20行）

## 強み
## リスク
## バリュエーション所見
## 総合投資判断
```

パーサは**ストリーミング途中の不完全なテキストにも呼べる**設計にしてあり、
届いた行から順に評価カードを描画できる。

### 中断（キャンセル）

```
フロント: requestId を採番 → invoke("llm_send", { request: { requestId, … } })
中断時  : invoke("llm_cancel", { requestId })
Rust    : CANCELLED に積む → SSE 読み取りループが次のチャンクで抜ける
          → それまでのテキストを Done { text, cancelled: true } で返す
```

中断してもそこまでの生成結果は破棄しない。

### 幻覚（ハルシネーション）対策

システムプロンプトで次を厳守させている。

- 提供資料に無いことを推測で断定しない
- 判断できない項目はスコア 0（判定不能）とし、根拠欄に明記する
- 数値の出所（財務指標 / SEC / 添付資料 / 一般知識）を根拠欄に含める

## 6.8 Step 4.1 詳細設計（実装済み）

### スマート圧縮 — 中間カットの廃止

**単純な head-tail（中間の一括削除）は完全に撤去した。**
決算資料や書き起こしでは、セグメント業績・ガイダンス・アナリスト Q&A といった
最重要情報が中盤に集中するため、中間を落とすと分析価値が失われる。

`src/lib/prompts/condense.ts` の手順:

1. **構造で分割** — 見出し・ページ区切り（`--- p.N ---`）・スライド区切り・
   `【…】`・`■`・`Item N.`・番号見出しなどを検出
2. **分析価値で採点** — キーワード（セグメント/ガイダンス/Q&A = 3点、売上/利益率 = 2点…）
   ＋ 数値密度 − 定型文（免責事項・将来見通しの注意書き = −5点）
3. **数値明細セクションを丸ごと優先確保** — セグメント別業績のような
   「同じ形の行が並び、大半に金額や増減率が入る」セクションは、
   一部だけ残すと**最も伸びている事業だけ欠けた表**になり誤読を招くため、
   予算の 60% 以内に収まるなら全量を確保する
4. **残りを配点 × 分量で按分** — 配点だけだと中身の詰まった節が痩せる
5. **はみ出す節は文単位で抽出** — 重要な文を**原文のまま**残す。
   要約ではないので事実の改変（幻覚）が起きない
6. **落とした箇所にマーカー** — `…（N文を省略）…` を必ず入れ、欠落を可視化

文の選び方で効いている工夫:

| 工夫 | 理由 |
| --- | --- |
| 長さのペナルティを 0.35 乗に弱める | トークン数で割ると短い文ばかり残り、情報量の多い文が落ちる |
| 単位つき数値（287億ドル / 14.1%）に強い加点 | 業績数値の行は分析にそのまま使える |
| Q&A は質問と回答を 1 単位に結合 | 片方だけ残っても分析に使えない |
| `Q:` / `A:` を見出しにしない | 1問1答を別セクションにすると Q&A だけで予算を食い尽くす |

SEC 提出書類も同様に、Item 単位で抽出したうえで各節をこの方式で圧縮する。

### 四半期推移とモメンタム

| 項目 | データ源 | 備考 |
| --- | --- | --- |
| 売上高・純利益（4Q） | Yahoo `incomeStatementHistoryQuarterly` | 全銘柄 |
| EPS 実績 / 予想 / サプライズ | Yahoo `earnings.earningsChart` | 4Q |
| **四半期 YoY** | SEC XBRL `companyconcept` | 米国上場のみ・30四半期分 |

> ⚠️ **Yahoo は四半期粒度で粗利・営業利益・キャッシュフローを返さない**（0 または null）。
> そのため四半期の利益率は純利益率のみを扱う。実 API で確認済み。

> ⚠️ **Yahoo の四半期履歴は 4 期分しか無く、そのままでは YoY を計算できない。**
> 季節性の強い企業（AAPL の 10-12 月期など）は QoQ だけでは成長の加速を判定できないため、
> 米国上場銘柄は SEC XBRL から過去分を取り、**期末日を約 1 年前と突き合わせて** YoY を出す。
> インデックスで 4 つ前を見る方法は、10-Q に第 4 四半期が含まれないため誤った比較になる。
> この方式で算出した AAPL の YoY (+16.4%) は Yahoo の公表値と一致することを確認済み。

UI（`QuarterlyTrend.tsx`）は売上高 / 純利益 / 純利益率 / EPS を切り替えられ、
YoY の拡大・縮小を「⏫ 成長が加速 / ⏬ 成長が減速」バッジで示す。

プロンプトには四半期テーブルとモメンタム判定を載せ、システムプロンプトで
**「YoY を主軸にする」「減速ならスコア 3 以下」「QoQ だけで加速と結論づけない」**
を厳守させている。
