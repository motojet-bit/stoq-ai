# Phase 2 設計書 — データパイプライン ＆ AI分析エンジン

## 1. 目的

ティッカー入力および PDF ドロップから、各種財務データ・一次資料テキストを取得し、
LLM（OpenAI / Anthropic / Gemini / OpenAI互換API）へ安全に渡して
**20項目のファンダメンタル分析**を生成・表示する。

---

## 2. 実装モジュール構成

| # | モジュール | 配置 | 役割 |
| --- | --- | --- | --- |
| 1 | API Key & Config Manager | `src/lib/config/` | 設定モーダル、APIキーの保持、プロバイダー選択状態の管理 |
| 2 | LLM Unified Engine | `src/lib/llm/` | OpenAI / Anthropic / Gemini / Custom の共通インターフェース |
| 3 | Financial Data Fetcher | `src/lib/api/` | Yahoo Finance（指標）/ SEC EDGAR（10-K・10-Q 本文） |
| 4 | PDF / Document Parser | `src/lib/parser/` | PDF テキスト抽出、トークン数カウンター、オーバーフロー警告 |
| 5 | Prompt Engine & Pipeline | `src/lib/prompts/` | 20項目プロンプトのパッキング、Markdown テーブルのパース |

```
[ユーザー操作: ティッカー入力 or PDFドロップ]
```

## 4. アーキテクチャ上の重要な決定

設計書の「モジュール構成」は `src/lib/` 配下に維持しつつ、
**実際のネットワーク呼び出しと秘密情報の保持は Rust（`src-tauri/`）側で行う。**
`src/lib/` の各モジュールは Tauri コマンドを呼ぶ薄いラッパとなる。

### 4.1 なぜ HTTP を Rust 側に置くのか

| 理由 | 詳細 |
| --- | --- |
| **CORS** | Yahoo Finance / SEC / 各 LLM API は WebView からの直接リクエストを CORS で拒否する |
| **User-Agent** | SEC EDGAR は連絡先入りの `User-Agent` を必須とするが、ブラウザは User-Agent の変更を禁止している |
| **秘密情報** | APIキーを WebView に渡さずに済む。キーは OS のアプリ設定ディレクトリに置き、フロントへはマスク済み文字列のみ返す |
| **Cookie** | Yahoo Finance の `crumb` 取得には Cookie セッションの保持が必要 |

```
┌─ フロントエンド (WebView) ────────────────┐
│  src/lib/config  src/lib/llm             │
│  src/lib/api     src/lib/parser          │  ← 実キーを一切保持しない
│  src/lib/prompts                         │
└───────────────┬──────────────────────────┘
                │ invoke() / Channel（ストリーミング）
┌───────────────▼──────────────────────────┐
│  src-tauri/src/                          │
│    settings.rs  … キー保存・マスク         │
│    llm/         … 4プロバイダ + SSE       │
│    yahoo.rs     … 指標取得（crumb 対応）   │
│    edgar.rs     … 10-K / 10-Q 本文        │
│    html.rs      … HTML → テキスト          │
└──────────────────────────────────────────┘
```

### 4.2 PDF パーサは `pdfjs-dist` を使う

設計書では `pdf-parse` を指定しているが、`pdf-parse` は Node.js 専用で `fs` に依存するため
WebView（ブラウザ環境）では動作しない。クライアントサイド抽出の標準である
**`pdfjs-dist`** を採用する。抽出はフロント側で完結し、PDF の中身はディスクに残さない。

### 4.3 `temperature: 0.0` の扱い

決定論的出力のため `temperature: 0.0` を固定するが、**プロバイダによって扱いが異なる**。

| プロバイダ | temperature | 備考 |
| --- | --- | --- |
| OpenAI | `0.0` を送信 | |
| Gemini | `0.0` を送信 | |
| OpenAI互換 (DeepSeek 等) | `0.0` を送信 | |
| Anthropic | **送信しない** | Claude Opus 5 では `temperature` パラメータ自体が廃止され、送ると HTTP 400 になる。深さの制御は `output_config.effort` で行う |

## 6. Step 1 詳細設計（実装済み）

### 6.1 設定の保存場所

```
%APPDATA%\com.stockanalyzer.desktop\settings.json
```

- APIキーはこのファイルにのみ存在し、**フロントエンドへは生の値を返さない**
- フロントへ返すのは `configured: boolean` と `masked: "sk-…3f9a"` のみ
- `.env` の `VITE_*` 方式（Phase 1 の暫定実装）は廃止

### 6.2 設定項目

| 項目 | 内容 |
| --- | --- |
| プロバイダ選択 | 組み込み 3 種 + ユーザーが追加した OpenAI互換プロバイダ |
| APIキー | プロバイダごとに 1 つ（カスタムも同じ辞書で管理） |
| モデル名 | プロバイダごとに 1 つ |
| SEC User-Agent | `アプリ名 メールアドレス` 形式。SEC が必須とする |
| 最大プロンプトトークン | プロンプトパッキングの上限（既定 180,000） |

#### プロバイダのデータモデル

プロバイダは 2 種類に分かれる。

| 種別 | ID | 追加・削除 |
| --- | --- | --- |
| 組み込み | `openai` / `anthropic` / `gemini`（固定） | 不可 |
| OpenAI互換 | `custom-<採番>` | **可変長リスト。UI から自由に追加・削除できる** |

```rust
struct CustomProvider { id, label, base_url, model }

struct Settings {
    provider: String,                    // 組み込み ID または カスタム ID
    models: BTreeMap<String, String>,    // 組み込みのモデル名
    keys: BTreeMap<String, String>,      // プロバイダ ID → APIキー（組み込み・カスタム共通）
    custom_providers: Vec<CustomProvider>,
    ...
}
```

- APIキーは**組み込み・カスタムを区別せず同一の辞書**で管理するため、
  マスク表示・保存・削除のロジックが 1 本で済む。
- カスタム枠を削除すると、対応する APIキーも同時に破棄される。
- 選択中のプロバイダを削除した場合は組み込みへ自動的に戻す。
- 旧形式（カスタム枠が 1 つ固定だった頃の `custom_base_url`）は
  設定読み込み時に自動でリストへ移行する。
- カスタムプロバイダを配列として保持することで、
  将来の**複数 LLM の直列/並列検証**から個別に呼び出せる。

### 6.3 LLM Unified Engine

`src-tauri/src/llm/` に 4 プロバイダの実装を置き、共通の `LlmRequest` を受けて
**Tauri の Channel でトークンをストリーミング**する。

```
LlmRequest { provider?, system?, messages[], maxTokens? }
   ↓ invoke("llm_send", { request, onEvent: Channel })
LlmEvent = Start  { provider, model }
         | Delta  { text }        ← 逐次描画
         | Done   { text, ... }
         | Error  { message }
```

| プロバイダ | エンドポイント | 認証ヘッダ | ストリーム形式 |
| --- | --- | --- | --- |
| OpenAI | `POST /v1/chat/completions` | `Authorization: Bearer` | SSE `choices[0].delta.content` |
| Anthropic | `POST /v1/messages` | `x-api-key` + `anthropic-version` | SSE `content_block_delta.delta.text` |
| Gemini | `:streamGenerateContent?alt=sse` | `x-goog-api-key` | SSE `candidates[0].content.parts[].text` |
| OpenAI互換 | Base URL + `/chat/completions` | `Authorization: Bearer` | OpenAI と同形式（実装を再利用） |

Anthropic 固有の扱い:
- `temperature` は送らない（400 になるため）
- `output_config.effort` で思考の深さを制御
- `stop_reason: "refusal"` を検知してユーザーに通知
- `fallbacks: "default"` を有効化し、拒否時に自動で代替モデルへ回す

### 6.4 UI

- **設定モーダル**: メニューバーの「ファイル > 設定…」「ヘルプ > …」、および
  上部の APIキー状態インジケーターのクリックで開く
- **対話パネル**: メイン下部のスプリット右側。テストメッセージを送信して
  ストリーミング応答を確認できる（疎通確認）

## 6.5 Step 2 詳細設計（実装済み）

### Yahoo Finance

`quoteSummary` は 2024 年以降 Cookie と crumb（CSRF トークン）を要求する。手順は次のとおり。

```
1. GET https://fc.yahoo.com/                       → Cookie を受け取る（404 が正常）
2. GET .../v1/test/getcrumb                        → crumb（プロセス内にキャッシュ）
3. GET .../v10/finance/quoteSummary/{symbol}?...&crumb=...
   → 401 なら crumb を捨てて 1 回だけ再取得
```

株価だけは crumb 不要の `chart` エンドポイントからも取れるため、
**`quoteSummary` が失敗しても株価・銘柄名・通貨は返す**（`warning` に理由を入れる）。

取得する指標は 6 グループ 36 項目。

| グループ | 項目 |
| --- | --- |
| 株価・規模 | 時価総額 / EV / 52週安値・高値 / ベータ / 発行済株式数 |
| バリュエーション | PER（実績・予想）/ PBR / PSR / EV·EBITDA / EV·売上高 |
| 成長性 | 売上成長率 / EPS成長率 / 四半期利益成長率 / EPS（実績・予想）/ 売上高 |
| 収益性 | 粗利率 / 営業利益率 / 純利益率 / EBITDAマージン / ROE / ROA |
| キャッシュ・財務健全性 | フリーCF / 営業CF / 現金 / 有利子負債 / D/E / 流動比率 |
| アナリスト予想 | 目標株価（平均・高・低）/ レーティング / 推奨スコア / アナリスト数 |

割合の扱いに注意が必要。Yahoo は `returnOnEquity` などを小数（0.4523）で返す一方、
`debtToEquity` は既に百分率（78.445）で返すため、整形関数を分けている。

### SEC EDGAR

**本文をダウンロードしない軽量なステータス照会**（`fetch_status`）を追加した。
`submissions/CIK##########.json` の `filings.recent` を走査し、
10-K / 10-Q の最新 1 件（提出日・対象期間・URL）だけを返す。

「EDGAR に登録がない」「User-Agent 未設定」は**エラーではなく状態として**返す。
非米国上場銘柄（例: 7203.T）でも Yahoo の指標表示を止めないため。

| `status` | 意味 | インジケーター |
| --- | --- | --- |
| `ok`（10-K と 10-Q 両方） | 分析に必要な資料がそろっている | 🟢 |
| `ok`（片方のみ） | 一部のみ取得可能 | 🟡 |
| `userAgentMissing` | 設定すれば取得できる | 🟡 |
| `noFilings` | 直近に 10-K / 10-Q がない | 🟡 |
| `notInEdgar` | 構造的に取得不可（非米国上場など） | 🔴 |

### UI の流れ

```
ティッカー入力 →「分析」
  ↓
分析タブを開く（既存なら切り替え）
  ↓
loadTicker(ticker) — YF と SEC を並行実行
  ↓                        ↓
指標カード（6枚）         資料準備インジケーター
  ├ 取得中: スケルトン      ├ 取得中: スピナー
  ├ 成功  : 実データ        └ 完了  : 🟢/🟡/🔴 + 提出日
  └ 失敗  : エラー + 再試行ボタン
  ↓
失敗時はトースト通知（右下、種類ごとに自動消去時間が異なる）
```

片方が失敗しても他方の表示は止めない。

## 7. 20項目のファンダメンタル評価（Step 4 で実装）

評価項目は `src/lib/prompts/criteria.ts` に **1 ファイルで定義**し、
差し替えやすくする。初期案は以下（ユーザーの確定待ち）。

| # | 項目 | # | 項目 |
| --- | --- | --- | --- |
| 1 | 事業モデルの明瞭さ | 11 | 資本配分の巧拙 |
| 2 | 競争優位（モート） | 12 | 経営陣の質・実行力 |
| 3 | TAM と成長余地 | 13 | ガイダンスの信頼性 |
| 4 | 売上成長の持続性 | 14 | セグメント別トレンド |
| 5 | 粗利率の水準と推移 | 15 | 顧客集中リスク |
| 6 | 営業レバレッジ | 16 | 規制・訴訟リスク |
| 7 | フリーキャッシュフロー創出力 | 17 | 景気感応度 |
| 8 | バランスシートの健全性 | 18 | バリュエーション妥当性 |
