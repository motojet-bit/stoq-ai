## 1. 決算期のユーザー承認ダイアログ

### やること

PDF を解析したあと、自動特定した決算期をユーザーに確認・修正させるステップを挟む。

> アップロードされた資料は **FY2023 Q3** のものです。この期として記録してよろしいですか？

- 「はい」で確定、「違う」で年度・四半期を手で選び直せる
- 修正した内容がそのまま分析と保存に使われる

### なぜ必要か

`detectFiscalPeriod` は**判別できなければ `null` を返す**ようにしてあるので、
黙って誤った期で進むことは無い。問題はその逆で、**読み取れてしまったが間違っている**場合。
決算資料には前年同期や中期計画の年度も書かれているため、表紙の書式が変わっていると
別の期を掴むことがある。これは機械的には検出できない。

期を取り違えると、**当時の株価・四半期指標として別の期の数値が突き合わされる**。
分析そのものは成立してしまうので、出力を読んでも間違いに気づけない。
ここは人が 1 回見れば確実に分かるので、確認を挟む価値が大きい。

### 実装メモ

- 判定ロジックは `src/lib/parser/fiscalPeriod.ts` に揃っている（`detectFiscalPeriod` /
  `matchQuarter` / `periodKey`）。UI から呼ぶだけで足りる
- 突き合わせ結果は `src/lib/prompts/periodLink.ts` の `PeriodLink`
- **`null`（判別できなかった）ときも同じダイアログを出す。** 「分かりませんでした、
  選んでください」と聞けば、資料の期を保存できる。いまは黙って期なしで進んでいる
- 確定した期は分析結果と一緒に保存したい（`analyses` テーブルに列を足す）。
  そうしないと、あとからヒートマップの期と突き合わせられない
- **毎回聞くと邪魔になる。** 「今後この資料形式では確認しない」は入れない方がよいが、
  自動特定と一致していて、かつ突き合わせも成功しているときは
  トースト表示だけにする案は検討の余地あり

## 2. SEC 自動フォールバック（10-K / 10-Q）

### やること

ユーザーが PDF を添付していない場合、SEC から該当ティッカーの最新
10-Q（四半期）または 10-K（年次）を自動取得して分析に使う。

### なぜ必要か

いまは資料なしでも分析できるが、**一次資料の裏付けが無いぶん精度が落ちる**。
米国上場銘柄なら SEC に必ず提出書類があるので、取りに行かない理由が無い。
「PDF を用意しないと本気の分析にならない」という敷居を下げられる。

### 実装メモ

- 取得の口はすでにある。`src-tauri/src/edgar.rs` の `fetch_status`（軽量な状況確認）と
  本文取得。`commands.rs` から呼ばれている
- **10-Q を優先し、無ければ 10-K。** 直近の状況を見たいので四半期が先
- **User-Agent 未設定なら取りに行かない。** SEC は 403 で弾く。
  `normalize_user_agent` がメールだけの入力を補完するので、
  メールさえ入っていれば動く
- **非米国上場（例: 7203.T）は EDGAR に無い。** `fetch_status` が
  `notInEdgar` を状態として返すので、これをそのまま「資料なしで続行」に落とす。
  エラーにしない（既存の方針と同じ）
- 10-K は非常に大きい。`buildPrompt` の予算配分（いまは資料 55% / SEC 45%）に
  そのまま乗るが、**添付ゼロなら SEC へ全部回してよい**
- 自動取得したことを画面と分析結果に明示する。
  ユーザーが渡していない資料が根拠に入るので、黙って使わない
- 参照は `【参照: SEC 10-Q】` の形（`prompts/core.md` に規定済み）

## 3. アドホック分析の入れ子ツリー管理（Q2-01, Q2-02）

### やること

四半期決算の合間に出る単発の開示（プレスリリース・適時開示・8-K 等）を分析したとき、
メインの四半期の下にぶら下げて記録する。

```
AAPL
├─ FY2024-Q2          （四半期決算の分析）
│   ├─ Q2-01          （5/10 の新製品発表）
│   └─ Q2-02          （6/02 の増資リリース）
└─ FY2024-Q3
```

### なぜ必要か

いまの保存は **1 銘柄 × 1 期で 1 レコード**なので、期の合間の分析を入れる場所が無い。
同じ期に複数回分析すると「最新の 1 件」として上書き扱いになる
（`buildHeatmap` が `savedAtMs` の新しいほうを採る）。
決算の間に起きた出来事を追いたい人にとっては、ここが抜けている。

### 実装メモ

- 保存は `src-tauri/src/analyses.rs`。`analyses` / 履歴テーブルに
  **親子関係の列**（`parent_id` と連番）を足す必要がある
- 連番は `Q2-01` のように**親の期＋通し番号**。表示用の文字列であって、
  内部キーは既存どおり ID で持つ（i18n の C グループ方針と同じ）
- ヒートマップ（`src/lib/portfolio/heatmap.ts`）は
  **列＝四半期**で組んでいるので、アドホックはセル内の件数バッジにするか、
  タイムライン側だけで見せるかを決める必要がある。列に混ぜると表が崩れる
- タイムライン（`PortfolioHistoryPanel`）は入れ子表示に改造する。
  削除は既に 1 件ずつできるが、**親を消したときに子をどうするか**を決める
  （CASCADE で一緒に消すか、孤児にして期の直下へ上げるか）
- 決算期の自動特定（項目 1）と組み合わせると、
  「この資料は FY2024-Q2 の期中のものです → Q2 の下に置きますか？」まで案内できる

## 進め方の順序（案）

1. **決算期の承認ダイアログ** — 既存ロジックの上に UI を載せるだけで、
   いま静かに間違いうる箇所を潰せる。費用対効果が最も高い
2. **SEC 自動フォールバック** — 取得の口が揃っているので次に軽い
3. **入れ子ツリー** — DB のスキーマ変更を伴うので最後。
   移行（`ALTER TABLE`）が要るぶん、前 2 つとは重さが違う
